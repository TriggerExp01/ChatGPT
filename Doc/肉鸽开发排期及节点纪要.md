### 节点级任务规划

#### 节点 1：2026-06-14 前，技术方案冻结

目标：

- 停止原型继续无边界扩张，先把技术底座和模块边界定死

具体任务：

1. 梳理现有肉鸽原型代码职责
2. 将肉鸽逻辑拆分为以下模块边界：
   - `Run`：单局状态、房间推进、结算
   - `Combat`：实时战斗、伤害、技能、敌人行为
   - `Progression`：遗物、升级、局内成长
   - `Config`：配置表加载、索引、校验
   - `UI`：局内 HUD、奖励、商店、结算
3. 明确“轻操作肉鸽”的最小交互模型：
   - 左侧移动
   - 自动普攻
   - 一个主动技能
   - 一个闪避/位移
4. 输出配置表清单
5. 输出正式 UI 信息架构草图
6. 停止把新规则继续塞进临时 HUD

验收标准：

- 有明确模块划分
- 有配置表目录和字段草案
- 有正式 UI 页面清单
- 有轻操作战斗输入定义

主要风险：

- 继续在现有 UI 上叠逻辑，后续拆分成本会快速上升

#### 节点 2：2026-07-15 前，配置化完成

目标：

- 将内容从代码硬编码迁移到配置，代码只保留规则解释和运行时拼装

具体任务：

1. 设计并落地以下配置表：
   - 敌人表
   - 精英/Boss 表
   - 遗物表
   - 升级选项表
   - 商店商品表
   - 房间奖励表
   - 事件选项表
2. 接入现有 `Configs/GameConfig` 和 Luban 生成流程
3. 把 [RoguelikeContentCatalog.cs](D:/Work/Unity_Project/TEngine_Game/UnityProject/Assets/GameScripts/HotFix/GameLogic/Roguelike/RoguelikeContentCatalog.cs:1) 中的内容定义迁到配置
4. 把 [RoguelikeGame.cs](D:/Work/Unity_Project/TEngine_Game/UnityProject/Assets/GameScripts/HotFix/GameLogic/Roguelike/RoguelikeGame.cs:1) 中的奖励池、营火池、宝箱池、商店池迁到配置
5. 增加配置校验：
   - 重复 ID
   - 缺失引用
   - 数值越界
   - 空池子
6. 做一版运行时配置索引缓存，避免战斗中频繁查表拼对象

验收标准：

- 内容不再靠代码硬编码维护
- 配置生成和运行时读取稳定
- 改数值或增内容不需要改核心逻辑代码

主要风险：

- 只迁一半会形成“双源配置”，后面最难维护

#### 节点 3：2026-08-31 前，轻操作战斗可玩

目标：

- 从当前文本/流程驱动战斗，升级为实时轻操作战斗原型

具体任务：

1. 实现玩家控制器
   - 移动
   - 朝向
   - 受击反馈
   - 死亡
2. 实现自动普攻系统
   - 搜敌
   - 攻击间隔
   - 伤害结算
3. 实现主动技能系统
   - 冷却
   - 触发
   - 技能效果接口
4. 实现闪避/位移
5. 实现敌人基础 AI
   - 巡航/追击
   - 近战攻击
   - 基础受击/死亡
6. 实现最小战斗房间流程
   - 入场
   - 清怪判定
   - 战斗结束
7. 内容目标：
   - 3 个普通敌人
   - 2 个精英敌人
   - 1 个 Boss

验收标准：

- 单个战斗房间可以完整游玩
- 战斗不再依赖文本模拟
- 玩家输入能明显影响战局结果

主要风险：

- 如果同时做过多技能和敌人行为，战斗层会拖跨后续排期

#### 节点 4：2026-10-15 前，完整单局闭环

目标：

- 从“可玩单房间”推进到“可玩完整一局”

具体任务：

1. 接通房间流程：
   - 起点
   - 战斗
   - 精英
   - 宝箱
   - 营火
   - 商店
   - Boss
2. 实现路线推进和房间进入逻辑
3. 实现局内奖励选择和成长应用
4. 实现商店购买、金币结算、离开逻辑
5. 实现失败结算和胜利结算
6. 实现单局基础掉落和成长曲线
7. 增加最小调试工具：
   - 跳房间
   - 加金币
   - 加遗物
   - 强制胜利/失败

验收标准：

- 可以从开始打到 Boss 结束
- 每类房间都能稳定进入和退出
- 单局成长、奖励、结算全部闭环

主要风险：

- 战斗和流程层若相互耦合过深，会导致后续 UI 接入非常痛苦

#### 节点 5：2026-11-30 前，正式 UI 版

目标：

- 用正式 UI 替换临时动态 HUD，让外部试玩者能直接理解并操作

具体任务：

1. 设计并实现局内正式 HUD：
   - 生命
   - 技能冷却
   - 金币
   - 遗物摘要
   - 当前房间/小地图信息
2. 设计并实现奖励选择面板
3. 设计并实现商店面板
4. 设计并实现营火/宝箱事件面板
5. 设计并实现暂停面板和结算面板
6. 清理旧 `BattleMainUI` 临时原型职责，按 HUD、控制、奖励、结算拆分 prefab 与代码
7. 统一中文文案、按钮交互、层级、关闭逻辑

验收标准：

- 不看日志也能完成一局
- UI 不再承担核心业务逻辑
- 所有关键交互都有可视反馈

主要风险：

- 如果到这个阶段还没把逻辑和 UI 分开，正式 UI 会变成第二套临时代码

#### 节点 6：2026-12-31 前，Beta

目标：

- 从“功能齐”推进到“有重复游玩价值”

具体任务：

1. 扩充内容池：
   - 敌人
   - 遗物
   - 商品
   - 事件
   - Boss 机制
2. 做数值平衡：
   - 玩家成长曲线
   - 房间收益
   - 商店经济
   - Boss 强度
3. 清理无效内容：
   - 必选选项
   - 明显垃圾选项
   - 纯换皮内容
4. 增加基础性能和稳定性检查
5. 组织内部试玩反馈，整理问题单

验收标准：

- 至少能支撑多人反复试玩
- 不会出现明显单一最优套路
- 关键体验问题可被稳定复现和修复

主要风险：

- 内容扩充过快但不做平衡，会让 Beta 失去判断价值

#### 节点 7：2027-01-15 前，封版候选

目标：

- 锁需求，集中做稳定性、性能和交付质量

具体任务：

1. 修复高优先级 bug
2. 清理运行时异常和错误日志
3. 做打包验证：
   - 启动
   - 进入单局
   - 打完整局
   - 结算
4. 做性能检查：
   - 战斗房间
   - 怪物密集场景
   - UI 打开/关闭
5. 整理版本说明和测试清单
6. 冻结大需求，只允许修 bug 和必要优化

验收标准：

- 可以给外部演示和试玩
- 没有阻塞级 bug
- 没有游戏自身的高频异常日志

主要风险：

- 春节前最后阶段继续插入新功能，会直接破坏封版质量
