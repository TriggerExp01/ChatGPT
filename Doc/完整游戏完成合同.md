# 《仙途·天命》完整游戏完成合同

## 1. 合同状态

本合同将当前项目从“TEngine 上的 Cultivation 原型”正式收束为需要持续完成的单机游戏项目。

- 正式产品名：`仙途·天命`。
- 产品类型：东方玄幻卡牌构筑 Roguelite。
- 首发平台：Windows / Steam。
- 核心体验：用卡牌构筑表现功法、门派、境界突破与渡劫修行。
- 当前权威范围：本合同、`Doc/设计文档/GDD_东方玄幻卡牌Roguelite.md` 的 v1.0 范围，以及后续阶段交付说明。
- 当前用户已授权 Codex 持续推进到完整游戏结束，不再逐项询问产品、玩法或实现选择。

“完成一个原型阶段”“测试全绿”或“能够跑一段流程”均不等于游戏完成。只有本合同的完成标准全部有当前证据时，才允许声明目标完成。

## 2. 产品支柱

1. **构筑即修行**：牌组不是单纯数值集合，每个门派和流派必须形成可辨认的策略身份。
2. **信息透明**：敌人意图、牌库、资源和关键概率必须可观察，决策深度不依赖盲猜。
3. **每次 Run 有独特路线**：地图、奖励、事件、构筑与法宝组合需要产生可复玩的差异。
4. **局内外双层成长**：境界突破构成 Run 内成长，道基树与门派解锁构成跨 Run 成长。
5. **先完整可玩，再扩内容**：每次扩展都必须连接进真实主循环，禁止只堆孤立代码、测试数据或不可进入的 UI。

## 3. v1.0 必须完成范围

### 3.1 微观战斗循环

- 抽牌、手牌、牌库、弃牌堆、消耗堆。
- 灵力、出牌费用、目标选择、回合结束。
- 玩家与敌人 HP、护盾、防御、伤害、治疗。
- 敌人意图与可预测 AI。
- 状态、修饰器、五行和门派协同。
- 胜利、失败、战斗统计与奖励结算。
- 可操作、可读、带基本动画和音效反馈的正式战斗 UI。

### 3.2 一次完整 Run

- 炼气、筑基、金丹、元婴、化神五层境界。
- 普通战斗、精英、坊市、闭关、秘境、宝箱、Boss / 天劫节点。
- 可预览、有限制且不可回退的路线选择。
- 卡牌三选一与跳过、卡牌升级、移除、购买和出售。
- 法宝、丹药、灵石、事件与奖励池。
- 境界突破、金丹被动、Boss 阶段和最终渡劫。
- Run 胜利、陨落、结算、返回主菜单与重新开局。

### 3.3 内容规模

- 6 个门派：剑宗、火云宗、药王谷、天雷阁、玄黄宗、魔道。
- 至少 120 张可用卡牌，包含门派卡、通用卡、丹药和秘术。
- 五层境界对应的普通敌人、精英和 Boss；设计文档中的敌人清单需要全部配置化并可进入真实 Run。
- 至少 15 件可用法宝，以及足够支撑多次 Run 的秘境事件、奖励和坊市内容。
- 道心难度 1-20、完整道基树、门派解锁和每日修行。

### 3.4 产品体验

- 主菜单、门派选择、难度选择、路线、战斗、事件、奖励、坊市、闭关、卡库、设置、结算页面齐全。
- 全部页面采用统一的东方水墨、暗玉、旧金视觉语言。
- MainRoute 以 `Doc/UI参考图/Phase78_Targets/Target_MainRoute.png` 为当前构图与品质基准；先完成一个黄金样板，再扩展其他界面。
- 简体中文、繁体中文、英文三种语言。
- 音乐、按钮反馈、战斗音效、关键成长和 Boss 反馈齐全。
- 键鼠操作完整；分辨率、音量、语言和基础画面设置可保存。

### 3.5 技术与发布

- 正式入口覆盖 `Procedure -> GameApp -> Cultivation`，Editor 快速入口只作为调试工具。
- 玩法逻辑与 UI 分离，Cultivation 业务不由 UI Service 或 MonoBehaviour 长期总控。
- 卡牌、敌人、事件、奖励、路线、门派和数值逐步迁移到 Luban 配置链路。
- 支持本地存档、版本迁移、失败恢复和 Steam 云存档接口。
- Steam 成就与发布所需基础集成完成；每日排行若外部服务不可用，至少保留可替换接口和本地每日种子体验。
- Windows Player 构建可安装或直接运行，完整 Run 无崩溃、无阻塞、无新增 Error。

## 4. 明确不做的 v1.0 范围

- 多人、PvP、合作模式。
- 移动端移植。
- 关卡编辑器、无尽模式。
- 大规模剧情对话系统。
- 卡牌皮肤和额外门派 DLC。
- 恢复已删除的旧肉鸽业务代码、旧 UI Prefab 或 `Roguelike_StarUI_*` 资产。

## 5. 持续实施顺序

### 阶段 A：可信基线

- 修复 Fast Enter Play Mode 假阳性。
- 修复 Editor 重复初始化与运行状态重置。
- 建立真实启动链路、构建和测试证据。
- 清理验证报告、文档编码和工作区噪声规则。

### 阶段 B：单层可玩垂直切片

- 将 Phase82 占位战斗替换为已有 `BattleEngine` 真实卡牌战斗。
- 串联一层地图、战斗、事件、奖励、坊市、闭关、Boss 和结算。
- 将运行状态从 UI 控制器抽到纯 C# Run 模型。
- 保存并恢复进行中的 Run。

### 阶段 C：正式视觉与交互

- 完成 MainRoute 黄金样板和统一主题资产包。
- 依次完成 Battle、Event、Reward、Market、Rest、CardLibrary 和 RunResult。
- 每次只推进 1-3 个 Prefab，并进行 1920x1080 截图验收和实际交互验证。

### 阶段 D：五层完整 Run

- 境界、突破、金丹被动、法宝、丹药与天劫机制进入真实流程。
- 五层敌人和 Boss 全部配置化、可达、可结算。
- 完成基础数值模拟和至少一条稳定可通关构筑。

### 阶段 E：六门派与跨 Run 成长

- 六门派全部完成卡池、初始牌组、核心机制和解锁条件。
- 道基树、道心 1-20、每日修行、成就与统计完成。
- 建立多次 Run 的可玩性与解锁节奏。

### 阶段 F：发布收口

- 本地化、音频、设置、分辨率与输入体验完成。
- Steam 接口、云存档和成就完成或提供可验证替代层。
- 全量 EditMode、PlayMode、自动走局、Player 构建和人工试玩验收通过。
- 发布包、版本说明、版权台账和已知问题清单齐全。

## 6. 每阶段硬门槛

每个阶段结束前必须同时具备：

1. 当前提交对应的代码、配置或资产。
2. 与范围匹配的测试，而不是仅用窄测试证明广泛结论。
3. `dotnet build UnityProject/UnityProject.sln --no-restore` 通过。
4. `git diff --check` 通过。
5. 涉及 Unity 行为时有当前 Unity MCP / Test Runner / Player 证据。
6. 涉及 UI 时有当前截图和可读性验收。
7. 中文交付说明记录已完成、未完成、入口和验证差异。
8. 阶段独立提交并推送，避免把布局噪声或无关文件混入。

## 7. 最终完成判定

最终完成审计必须逐项证明第 3 节全部成立。以下证据不能单独作为完成证明：

- 旧提交或旧报告中的 PASS。
- 只通过编译但没有运行验证。
- 只运行逻辑测试但没有真实 UI / Player 路径。
- 只有 UI 截图但页面没有连接业务流程。
- 只有种子数据或文档，内容未进入可玩 Run。
- 自动测试被强制 `Assert.Pass`、忽略失败信息或覆盖范围不足。
