# Phase76 交付说明：修仙原型主循环验收标准固化

## 结果摘要

本阶段先固化 `Cultivation / 修仙养成原型` 的主循环验收口径，不修改 C#、Prefab、配置表生成脚本或启动代码。

当前项目协作基线调整为：TEngine 骨架上已经接入修仙养成原型，后续可以围绕修仙、养成、路线选择、秘境事件和卡牌战斗继续收束；但这不是最终产品方向锁死。Phase76 的价值是先定义“什么叫当前原型主循环可验收”，避免继续堆零散功能却没有统一入口、统一证据和统一风险说明。

## 实际改动清单

- `AGENTS.md`
  - 将项目定位从“纯空工程骨架”调整为“TEngine 骨架 + 当前 Cultivation 修仙养成原型”。
  - 明确 Cultivation 是当前 Dev 分支默认原型方向，但不是最终产品方向锁死。
  - 保留禁止恢复旧肉鸽玩法、旧 UI Prefab、旧视觉资源的规则。
  - 明确 Editor 快速入口只属于原型调试入口，正式验收应区分 Procedure -> GameApp -> Cultivation 链路。
- `Doc/产品方向.md`
  - 新增当前原型方向说明。
  - 固化可推进、暂不默认推进、禁止恢复的边界。
  - 补充启动链路、业务模块、配置表和阶段验收方向。
- `Doc/交付说明/Phase76_修仙原型主循环验收.md`
  - 新增 Phase76 验收标准文档。
  - 明确后续真正验收主循环时需要收集的自动化、MCP、截图、日志和人工观察证据。

## Phase76 验收目标

Phase76 的目标不是一次性做完整游戏，而是把当前修仙原型收束成一个可复现、可观察、可继续迭代的最小主循环。

验收通过时，应能证明：

- 能进入 Cultivation 原型主界面。
- 能从固定初始状态开始一局原型流程。
- 能选择或推进路线节点。
- 能触发至少一个秘境事件。
- 能获得至少一种奖励，并在状态中可观察。
- 能覆盖休息、市场、宝箱、战斗等核心节点中的已实现部分。
- 能输出关键状态、操作序列、战斗或事件日志。
- 自动化验证和 Unity 控制台均没有新增阻断性错误。

## 必须区分的启动入口

### Editor 快速入口

用途：

- 快速打开 Cultivation 原型 UI。
- 快速检查局部界面、文案、事件和状态展示。
- 辅助调试 UI 原型。

限制：

- 不能单独证明正式 TEngine 启动流程可用。
- 不能单独证明热更入口或资源加载链路可用。
- 交付时必须标注它只是原型调试入口。

### 正式验收入口

正式验收应优先覆盖：

```text
Procedure -> GameApp -> Cultivation 业务入口
```

验收材料中需要说明：

- 是否通过 TEngine 标准 Procedure 链路进入。
- 是否经过 GameApp 热更入口。
- 是否最终进入 Cultivation 原型界面或回退入口。
- 如果正式链路未覆盖，必须列为未验证风险。

## 建议验收清单

### 自动化验证

- `dotnet build UnityProject\UnityProject.sln --no-restore` 通过。
- `git diff --check` 通过。
- Cultivation 相关 EditMode 测试通过。
- 如涉及 UI 或流程，PlayMode 测试通过。
- 固定种子、固定路线、固定卡组、固定敌人可以稳定复现。

### Unity MCP 与日志

- Unity MCP 能读取 Editor 状态。
- 至少一个操作型 MCP 工具可用，例如 `read_console`、`manage_scene`、`find_gameobjects`、`manage_camera` 或 `execute_code`。
- Unity 控制台无新增 Error。
- 生成 MCP 健康报告，报告路径放入 `Doc/MCPReports` 或交付说明中明确引用。
- 若出现 MCP 插件连接断线、流释放等工具层错误，需要和游戏代码错误分开说明。

### 原型流程观察

- 主界面进入成功。
- 当前角色、牌组、路线或关键资源状态可见。
- 路线推进后节点状态变化可见。
- 秘境事件展示当前抽中的事件、选项和结果。
- 奖励获得后能在状态或展示层观察到变化。
- 战斗节点能进入、结算并回到路线或阶段结果。
- 休息、市场、宝箱等节点如果尚未完整实现，需要明确标为部分覆盖或未覆盖。

### 截图与复盘证据

推荐在真正验收时输出：

- 原型主界面截图。
- 路线选择或路线推进截图。
- 秘境事件触发截图。
- 奖励获得截图。
- 战斗开始与结算截图。
- 操作序列记录。
- 关键状态快照。
- 控制台 Error 截图或日志摘要。

## 做与不做

### 本阶段做

- 固化当前 Dev 分支的协作基线。
- 固化 Cultivation 原型方向的边界。
- 固化 Phase76 主循环验收口径。
- 保留禁止恢复旧肉鸽内容的规则。

### 本阶段不做

- 不修改 C#。
- 不修改 Prefab。
- 不修改配置表或 Luban 生成脚本。
- 不修改启动代码。
- 不新增美术资源。
- 不把修仙方向写成最终商业产品锁定。
- 不恢复旧肉鸽玩法、旧 UI Prefab、旧视觉资源。

## 假设与风险

- 当前 Phase76 文档只定义验收标准，不代表这些验收项已经全部通过。
- 当前 Cultivation 原型已有逻辑和 UI 入口，但正式 Procedure -> GameApp 链路仍需要在后续阶段用证据确认。
- 如果后续只使用 Editor 快速入口试玩，可能出现“编辑器能跑，正式链路不能跑”的风险。
- 当前 UI 框架不等于视觉质量已经成立；真正 UI 样板仍需要参考图、黄金样板和截图 QA。
- 当前部分原型数据仍可能是 C# 种子数据，后续配置化前需要在交付说明中持续标注。
- 自动化测试可以证明状态转换和流程覆盖，不能替代人工对手感、节奏、审美的主观判断。

## 可选下一步

- 按本文档建立固定种子试玩局，并补齐截图、操作序列、状态日志和 MCP 健康报告。
- 将 Cultivation 原型中的事件、奖励、路线和角色数据分批迁移到 Luban 配置表。
- 逐步把 Cultivation 业务逻辑从 UI Service 中拆清，形成更明确的运行模型、事件系统、奖励系统和存档边界。
