# 产品方向：TEngine 骨架上的 Cultivation 修仙原型

## 结果摘要

当前 Dev 分支先按 **TEngine 骨架 + Cultivation / 修仙养成原型** 作为默认原型方向收束。

这份文档用于统一项目协作认知：当前仓库不再只是纯空骨架，代码已经接入修仙原型入口和部分卡牌、路线、秘境事件逻辑；但这也不代表最终商业产品方向已经锁死。后续仍需在阶段开始前确认玩法范围、视觉风格、资源选择和验收方式。

## 当前定位

- 工程底座：Unity + TEngine + HybridCLR + YooAsset + Luban。
- 当前原型方向：修仙 / 养成 / 路线选择 / 秘境事件 / 卡牌战斗。
- 当前阶段性质：业务原型收束期，不是正式产品化阶段。
- 当前重点：把已经存在的原型入口、主循环、验收标准和模块边界统一起来，避免继续堆零散功能。

## 已确认边界

### 可以继续推进

- Cultivation 修仙原型的主循环验证。
- 固定种子、固定路线、固定卡组、固定敌人的可复现试玩局。
- 秘境事件、奖励、路线、战斗、休息、市场、宝箱等最小闭环。
- 纯逻辑层测试、PlayMode 流程测试、Editor 验收器、MCP 健康报告、截图和日志复盘。
- 后续将事件、奖励、路线、角色、道具等内容逐步迁移到 Luban 配置链路。
- 后续将 Cultivation 业务能力从 UI Service 中拆出，沉淀为清晰的模型、系统或模块。

### 暂不默认推进

- 不把当前修仙原型写成最终产品方向锁死。
- 不提前承诺正式产品名、商业化卖点、完整世界观、美术风格或上线平台。
- 不在没有参考图和黄金样板的情况下批量制作 UI Prefab。
- 不在没有配置表方案确认前大规模硬编码事件、奖励、路线和数值。
- 不为了短期演示新建第二套平行框架。

### 禁止恢复

- 旧肉鸽玩法代码。
- 旧 Battle 系列 UI。
- 旧 UI Prefab。
- `Roguelike_StarUI_*` 和其他旧肉鸽美术资源。
- 旧演示截图、Steam 展示图、旧阶段路线和开发日志。
- Unity `UserSettings` 布局噪声。

## 启动链路认知

当前需要区分两类入口：

- Editor 快速入口：用于快速打开 Cultivation 原型 UI、检查界面和局部状态，不能单独代表正式链路通过。
- 正式验收入口：应优先覆盖 Procedure -> GameApp -> Cultivation 业务入口，证明热更/框架启动链路可以进入当前原型。

交付说明中必须明确本阶段验证覆盖的是哪条链路。如果只验证 Editor 快速入口，需要把正式链路列为未覆盖风险。

## 业务模块方向

当前 Cultivation 原型不应长期依赖 UI Service 作为业务总控。后续演进建议按阶段逐步拆清：

- Cultivation 运行状态模型。
- 路线与节点系统。
- 秘境事件系统。
- 奖励与掉落系统。
- 战斗逻辑与展示适配。
- 存档与读档数据。
- UI 展示服务。

拆分原则是先服务可验证主循环，不提前做大而全的框架。

## 配置表方向

新增业务配置优先走 `Configs/GameConfig` 和 Luban 生成链路。第一批适合沉淀的配置包括：

- 修仙事件。
- 奖励池。
- 路线节点。
- 角色或门派。
- 道具。
- 敌人与战斗数值。

在配置表正式落地前，可以保留少量 C# 种子数据用于测试和固定试玩局，但阶段交付需要说明哪些数据仍是临时硬编码。

## 阶段验收方向

后续每个阶段至少写清：

- 本阶段目标。
- 做与不做。
- Editor 快速入口是否验证。
- 正式 Procedure -> GameApp 入口是否验证。
- 逻辑测试、PlayMode 测试、MCP 控制台、健康报告、截图和日志的覆盖情况。
- 自动化已经证明的内容。
- 仍需要人工主观判断的手感、节奏、审美风险。

Phase76 先作为“修仙原型主循环验收”的收束阶段，用于把当前原型从零散功能整理成可复现、可观察、可继续迭代的主循环。
